  ---
  1. Paste Image из буфера обмена

  Твоя идея: кнопка "Paste Image" рядом с "Select files" в обеих дропзонах.

  Мой анализ: Идея хорошая, но есть нюансы:

  - navigator.clipboard.read() требует фокуса на страницу и разрешение
  пользователя (permission prompt). Это может раздражать.
  - Более надежный подход — слушать событие paste на document, где clipboardData
   доступен без промптов разрешений. Это стандартная практика (Google Docs,
  Discord, Slack — все используют paste event).

  Моё предложение:

  1. Кнопка "Paste" в дропзонах — да, добавить. При клике вызывать
  navigator.clipboard.read(). Если браузер не поддерживает или нет разрешения —
  показать подсказку "Press Ctrl+V to paste".
  2. Глобальный paste event — дополнительно ловить Ctrl+V / Cmd+V на странице.
  Если viewer закрыт и нет фокуса в текстовых полях — вставлять изображение из
  буфера. Вопрос: куда вставлять? Варианты:
    - Если ни одна batch-дропзона не открыта → создать новый батч (как через
  основную дропзону)
    - Если открыта batch-дропзона → добавить в этот конкретный батч

  ┌─ Drop zone ──────────────────────────────────────┐
  │  Drop images here or select up to 50 files...    │
  │  [Select files]  [Paste image]                   │
  └──────────────────────────────────────────────────┘

  ┌─ Batch drop zone ───────────────────────────────┐
  │  Drop images here to add to this batch           │
  │  [Select files]  [Paste image]                   │
  └─────────────────────────────────────────────────┘

  Вопросы к тебе:
  - Нужен ли глобальный paste (Ctrl+V без клика на кнопку)? Это удобнее, но
  может конфликтовать с вводом текста в title/description.
  - Буфер обмена может содержать несколько изображений (редко), но чаще одно.
  Одного достаточно?

  Сложность: Низкая-средняя. Clipboard API хорошо поддерживается. Основная
  работа — обработка Blob из clipboard и отправка на сервер как файл.

  ---
  2. Esc для выхода из Edit Mode

  Твоя идея: нажатие Esc закрывает Edit Mode.

  Мой анализ: Отличная идея, стандартный паттерн UX. Но нужна осторожность:

  - Сейчас Esc уже используется для закрытия viewer (строка 440 app.js).
  Приоритет: viewer > edit mode.
  - Нужно проверять: если viewer открыт — Esc закрывает viewer. Если viewer
  закрыт и edit mode активен — Esc выходит из edit mode.
  - Также: если фокус в текстовом поле (title/description input) — Esc должен
  сначала снять фокус (blur), а не выходить из edit mode. Иначе пользователь
  случайно выйдет, пока редактирует текст.

  Предлагаемая логика:
  Esc нажат:
    1. Viewer открыт? → закрыть viewer
    2. Фокус в текстовом поле? → blur (снять фокус)
    3. Edit mode активен? → выйти из edit mode

  Сложность: Очень низкая. Буквально ~10 строк кода в существующий keydown
  listener.

  3. Лайки / Избранное

  Твоя идея: сердечко на каждом thumbnail (левый нижний угол), кнопка-фильтр
  вверху, влияет только на fullscreen viewer.

  Мой анализ: Хорошая функция. Несколько важных вопросов:

  Хранение лайков

  Вариант A: В metadata.json — добавить поле liked: [filename1, filename2] в
  каждый batch (или favorites: [] на уровне tab).

  Вариант B: В localStorage браузера — персональные лайки, не синхронизируются
  между пользователями сети.

  Учитывая что это collaborative gallery, я бы рекомендовал Вариант A 
  (metadata.json) — лайки видны всем пользователям. Но это зависит от задачи:
  если лайки — личное дело каждого, то localStorage лучше.

  UI сердечка на thumbnail

  Твоё предложение — левый нижний угол. Согласен:

  ┌──────────┐
  │          │
  │   img    │
  │          │
  │♡        x│  ← ♡ всегда видно, x только в edit mode
  └──────────┘

  После клика:
  ┌──────────┐
  │          │
  │   img    │
  │          │
  │♥        x│  ← заполненное сердечко
  └──────────┘

  Важный нюанс: сердечко должно быть видно ВСЕГДА (не только в edit mode), но не
   должно мешать клику для открытия viewer. Решение: сердечко — отдельная
  кликабельная зона с e.stopPropagation(), как и кнопка удаления.

  Кнопка-фильтр вверху

  ┌─────────────────────────────────────────────────────────┐
  │  AI Image Gallery Manager                               │
  │  Organise AI generations...    [♡] [Toggle edit mode]    │
  └─────────────────────────────────────────────────────────┘

  При нажатии ♡ → ♥ (заполненная), viewer показывает только лайкнутые.

  Мои предложения по улучшению:

  1. Счетчик лайков — показывать число рядом с сердечком: ♡ 12 → ♥ 12. Так
  пользователь видит сколько отобрано.
  2. В viewer показывать сердечко тоже — чтобы можно было лайкать/снимать лайк
  прямо в полноэкранном режиме, не выходя. Это стандартная практика (Instagram,
  Google Photos). Маленькое сердечко в углу viewer.
  3. Визуальная индикация в обычном режиме — ты сказал "обычный режим не меняет
  отображение". Я согласен, но предлагаю лёгкий визуальный акцент — лайкнутые
  изображения в обычном режиме показывают заполненное сердечко, чтобы было видно
   что отмечено.

  Сложность: Средняя. Нужно: API эндпоинт для toggle like, изменение metadata
  schema, UI на thumbnail, UI на header, фильтрация в viewer navigation.

  - Если нужен экспорт по батчу — можно добавить маленькую кнопку Export в

  5. Поиск по промптам и заголовкам

  Твоя идея: кнопка Search или поле поиска вверху, переход в режим отображения
  найденных батчей, крестик для сброса.

  Мой анализ: Самая интересная и комплексная фича. Вот мои соображения:

  Расположение

  Я предлагаю inline поле поиска (не кнопку с выпадающим полем). Причина: один
  клик вместо двух, поиск всегда на виду. Но поле может быть компактным:

  ┌─────────────────────────────────────────────────────────────┐
  │  AI Image Gallery Manager                                    │
  │  Organise AI generations...                                  │
  │                          [🔍 Search...  ] [♡] [Toggle edit]  │
  └─────────────────────────────────────────────────────────────┘

  Поле сворачивается до иконки на мобильных. На десктопе — всегда видно.

  Режим поиска

  Согласен с твоей идеей: при вводе текста → показываются только батчи с
  совпадениями. Это фактически фильтрация.

  Обычный режим:               Режим поиска "sunset":
  ┌──────────────┐              ┌──────────────────────────┐
  │ Batch 5      │              │ 🔍 "sunset"          [x] │ ← инпут с крестиком
  │ Batch 4      │              │                          │
  │ Batch 3      │              │ Tab: Summer              │
  │ Batch 2      │              │ Batch 3 · "Golden sunset │
  │ Batch 1      │              │ over the mountains..."   │
  └──────────────┘              │ [img][img][img]           │
                                │                          │
                                │ Tab: Portraits           │
                                │ Batch 1 · "Sunset        │
                                │ portrait lighting..."    │
                                │ [img][img]               │
                                └──────────────────────────┘

  Ключевые решения:

  1. Поиск по всем табам — результаты группируются по табам. Это мощнее чем
  поиск только в текущем табе. Перед каждой группой батчей — заголовок таба.
  2. Подсветка совпадений — выделить найденное сочетание в тексте
  title/description (bold или highlight). Это сильно помогает пользователю.
  3. Выход из режима поиска:
    - Крестик [x] в поле поиска — очищает поле, возвращает в обычный режим
    - Клавиша Esc — если фокус в поле поиска, очистить и выйти
    - Пустое поле — автоматический возврат (debounced)
  4. Debounce поиска — не искать на каждый символ, а с задержкой 300ms. Поиск
  клиентский (вся metadata уже в памяти), так что будет мгновенно.
  5. Case-insensitive — очевидно, поиск без учёта регистра.

  Моё предложение по реализации:
  - Поиск полностью клиентский (данные metadata уже загружены, не нужен
  серверный API)
  - При вводе текста → фильтровать metadata.tabs[].batches[] по title и
  description
  - Заменить отображение batchList на отфильтрованные результаты,
  сгруппированные по табам
  - При клике на батч в результатах → переключить на соответствующий таб и
  прокрутить к этому батчу (или просто открыть его на месте)

  Сложность: Средняя. Основная работа — рендеринг результатов в кросс-табовом
  формате и UX перехода между режимами.

  По лайкам — структура в metadata.json

  Два варианта хранения:

  A) Поле liked в каждом batch:
  {
    "id": "b_abc123",
    "title": "...",
    "images": ["img1.png", "img2.png", "img3.png"],
    "liked": ["img1.png", "img3.png"]
  }

  B) Поле favorites на уровне tab:
  {
    "name": "Spring",
    "favorites": ["img1.png", "img3.png"],
    "batches": [...]
  }

  Рекомендую вариант A (в каждом batch). Причина: изображения уникальны в
  пределах batch, и при перемещении/удалении батча лайки перемещаются вместе с
  ним автоматически. В варианте B при перемещении batch в другой tab нужно
  переносить favorites отдельно — лишняя логика и источник багов.

  - Сейчас нет никакой модульной системы (нет bundler, нет ES modules в
  браузере). Чтобы разделить код и сохранить доступ к this (состояние

    - ES modules (import/export) — потребует <script type="module">, что меняет
  поведение (strict mode, CORS, deferred loading). Несложно, но это рефакторинг
  ради рефакторинга.
    - Несколько <script> тегов с глобальными функциями — хуже, чем один файл.
  Теряем инкапсуляцию.
    - Mixin-паттерн — вынести методы в отдельные файлы, подмешивать в prototype.
   Работает, но добавляет сложность без реальной пользы.
  - Все новые фичи тесно связаны с существующим кодом:
    - Paste — вплетается в upload flow
    - Esc — 5 строк в существующий listener
    - Лайки — затрагивает thumbnail рендеринг, viewer, header
    - Export — одна кнопка + один API call
    - Поиск — свой рендеринг, но использует те же структуры данных и viewer
  - 2800 строк для SPA без фреймворка — нормальный размер. Это не тот порог где
  разделение даёт реальную выгоду.

  Не разделять. Причины:

  3. 2800 строк — управляемый размер, особенно с хорошими именами методов
